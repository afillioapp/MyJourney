## Findings

### Confirmed violations

**V1. The server design has S-12 send the skip request when the user leaves capture. S-12 does not say so.** Rubric: R-165 (4) (updated), R-173 (2), R-175 (new). It does not block Phase 3. It blocks the S-12 flow (Phase 2) and screen (Phase 4).

- **Where:**
  - `Phase-1-Amendments.md:566`: "S-12 sends one request when the user skips, and the same request when it leaves capture without a page taken (`PROVISIONAL: C4`) … the screen row is ux's, R-173 (2)".
  - `Phase-1-Amendments.md:954` (OQ-39): "S-12 sends it on skip and on leaving capture".
  - `Phase-1-Amendments.md:59` (§0 WWW) and P1:108 say the same: "When the user skips or leaves capture, the device sends the route a skip request".
  - S-12 end (3) at `Screen-Inventory.md:340` reads only "the user leaves capture (`PROVISIONAL: C4`)". Reads at `:348` sends a skip on a skip only: "It also sends a skip, so that the route drops the note step for that press". Neither `:28` nor `:345` sends anything on leaving capture.
  - `Status.md:149`: "S-12 skip already carried by ux". ux carried the skip in b89299a (06:53). Lead-tech designed the leave-capture trigger 11 minutes later in 5e9f8a1 (07:04), and it never went back to ux.
- **What is wrong:** a Phase 4 builder who builds S-12 from its row sends the request on a skip and not on leaving capture. R-173 (1)'s route test still passes, because it sends the request straight to the route. The client then holds `PROVISIONAL: C4` by convention, and the route keeps the entry alive until the next press or press + 15 minutes.
- **Why it breaks the rule:** R-165 (4): when a doc says a behaviour is handled on a named screen, that screen's table carries it. R-173 (2) requires the device's skip **and its leaving capture** each to reach the route as a request. `CLAUDE.md:80–83`: rules are enforced in code, not by convention. BBBB (a) accepts outside code that never sends the request. It does not accept the product's own client failing to send it. What counts as "leaving capture" is itself unruled (G-28, N2).

**V2. FS §20 AAAA and BBBB are not addressed in Screen-Inventory, and AAAA's screen condition is on no S-02 row.** Rubric: R-165 (3) and (5), R-170 (4) (updated). It does not block Phase 3. It blocks the S-02 and S-12 rows (Phase 4).

- **Where:**
  - Neither letter appears in `Screen-Inventory.md` (scan above). Both were recorded at f8eb07e, after SI's last edit (b89299a). Nothing in SI says they do not bear.
  - OQ-38's question (`Phase-1-Amendments.md:953`) reads "Accept the residual for the prototype (S-02 must then not show the wait, R-170 (4))". AAAA (`FS:363`) accepted it. `:600` repeats it: "no transition into S-12 shows the wait in a way that would tell the user".
  - S-02 bans a wait indicator only on the guard-refusal row (`Screen-Inventory.md:95`: "A wait, busy or 'saving' indicator for the second strip"). The plain `sealed` row (`:93`) and the lost-press row (`:96`) have no such line, and neither does any S-12 row for the note press.
  - BBBB (b)'s `closed` is met by S-12's general "closed looks like the window having ended" (`:344`, `:348`). SI does not say that it covers BBBB.
- **What is wrong:** the measured gap is 16.7–21.1 ms on a press and 10.8–14.4 ms on a note press, and it falls only on the presses that met the bug (`Phase-1-Amendments.md:578–600`). A competent builder adds a busy indicator that appears only after a short delay, or only when the answer is slow. That turns an accepted server residual into a visible difference on exactly those presses. The difference is one the user can learn, and it invites a second press (R-170; R-160).
- **Why it breaks the rule:** R-165 (3): each §20 item recorded since a doc's last edit is carried, with its letter cited, or stated as not bearing. R-165 (5): an accepted residual is still checked against every screen whose behaviour it states. r9 V2 found the same pattern for SSS–XXX on P1:3: rulings went to one owner and not the other.

### Notes for Phase 4+ (and the Phase 2 flows)

**N1. Capture or the note step open at the unlock instant (G-27, new).** Rubric: R-171 (Decided line), R-168. Not picked.

- S-12 end (7) "looks exactly like (4)" and bans "nothing that sets end (7) apart from end (4)" (`Screen-Inventory.md:340`).
- S-12 then "leads to the camera S-02" (`:336`). S-02's `unlock-day` row is "Not available" (`:99`). After (4) the camera works and after (7) it does not, so the screen after the step differs whatever S-12 does.
- A press made on an open camera at or after unlock is answered `refused` (`Phase-1-Amendments.md:574`). S-02's only refusal row is "no frame, or the highlight's quota reached" (`:94`, B7), so the refusal would read as "no frame". DN C1 says "Your Journey is ready" appears on next open.
- Nobody has ruled whether an open camera changes at the unlock instant or only on the next open. The prototype reaches this case on every jump to the next unlock with capture open (R-153). A builder will pick, and both picks touch a never-list.

**N2. "Leaving capture" is not defined (G-28, new).** Rubric: R-175, R-173.

- Since WWW, leaving capture is a client event that sends a request (`Phase-1-Amendments.md:566`). No doc says whether the app going to the background, the screen locking, an incoming call or the system closing the app counts.
- A normal app resumes the note step on return. Under `PROVISIONAL: C4` ("there is no way back"), that would be a way back. Raise it with the user (rule zero); do not pick.

**N3. YYY's general words, "Nothing is added to a journey once it unlocks", are repeated outside their subject.** Rubric: R-174 (new).

- `FS:361` uses the phrase as the reason for the note window ending. `Screen-Inventory.md:340` end (7) and `:346` repeat it as a reason.
- Read literally, it bars the reveal: tags, chapters, feelings, visibility, reflections and the overview are all added to an unlocked journey (`CLAUDE.md:103`; FS §20 A).
- The build docs scope it correctly today: `Phase-1-Amendments.md:568–570` and P1:108 apply it to `add_note()` and the `note` trigger only. R-174 keeps it that way and adds a schema test that reveal writes still succeed after unlock.
- Not a conflict to raise: the ruling's subject is clear. The risk is a line copied without its subject.

**N4. The route's entry now holds the journey id, which "What the route writes" does not ban.** Rubric: R-169 (updated).

- `Phase-1-Amendments.md:562` adds "the id of the journey the press was into" to the in-memory entry, for YYY's bound.

- The same file says why it matters (`:946`): "a sealed journey's id beside a real time records that its owner pressed then".
